# DSH `0.1.2-alpha.1` Desktop Adaptation Record

## Summary

This record covers the Desktop transition from retained core `0.1.1-rc.2` to `0.1.2-alpha.1`. The target introduced authenticated Web startup, a decomposed client package graph, stricter extension registration, and fail-closed persisted data. Those changes exposed Desktop assumptions about URLs, Host ownership, mutable core directories, unversioned plugins, profile patches, and manual verification.

## Core changes

### Authenticated Web readiness

The Web bundle now waits for Loader settlement and the Connection service, creates a process-token URL through `connection.authenticatedUrl()`, prints that URL as the readiness signal, and hands the authenticated URL to the browser. The exchange establishes an HttpOnly `SameSite=Strict` Cookie; a clean origin URL without that exchange is not an authenticated application session.

This is a legitimate core security improvement. A supervisor must consume the announced URL without logging or persisting its token, preserve same-site navigation for the Cookie, and distinguish the external clean service URL from the credential-bearing WebView URL.

### Client package decomposition

The monolithic `@deepseek-ai/dsh-client-runtime` package was removed. Store infrastructure moved to `@deepseek-ai/dsh-client-store`, and Session, Workspace, Conversation, Chat, Approval and other responsibilities moved to domain-owned packages. The API Proxy transport was also retired in favor of Connection-owned and domain Remote interfaces.

Plugins compiled against `@deepseek-ai/dsh-client-runtime/client` therefore cannot activate on the target graph. A package name rewrite can bridge a narrow Store import, but a plugin that depended on removed Runtime behavior needs a source migration to the new domain owner.

### Loader and slot ownership

Client modules and UI slots now rely on explicit owner tables and late contribution through `ctx.slots.inject()`. A contributor that directly registers `settings.section` before its declaring owner arrives can fail activation instead of being silently accepted in incidental load order.

This change makes extension ownership deterministic. Plugin artifacts must declare the packages that materialize their client modules and must contribute into late-owned slots through the supported injection path.

### Host trust and browser privilege

The target separates WebRuntime authority from Connection browser privilege. Route owners read `ctx.webRuntime.trustedHosts`; settings persistence and Host API access rely on the Connection view of whether the browser owns a local Host. An embedded alias is not automatically equivalent to the literal `127.0.0.1` origin.

Desktop must therefore state two independent facts: DSH accepts `dsh.tauri.localhost` as a trusted runtime authority, and the embedded browser owns that loopback-only Host. Setting only a Connection route value does not update route owners; setting only runtime trust does not grant settings persistence.

### Persisted session vocabulary

The target reads persisted session events against a required vocabulary and rejects unknown event types. The prerelease line makes no cross-version session-format promise, so `0.1.1-rc.2` can reject a session written by `0.1.2-alpha.1`.

Desktop must surface this refusal without crashing or rewriting events. Silent conversion would invent core semantics and make later recovery less reliable.

## Observed conflicts

| Symptom | Immediate cause | Root cause |
| --- | --- | --- |
| `ERR_CONNECTION_REFUSED` or a blank shell after launch | Desktop navigated before the authenticated readiness URL was available | Lifecycle code treated a listening port as complete Web readiness and exposed one URL for both display and authenticated navigation |
| Plugin Loader reported a missing module table for `dsh-client-runtime/client` | RC-era plugin bundles imported a package entry removed from the target | Plugins were not pinned and built per client ABI generation; Desktop assumed npm package compatibility from package names alone |
| Better Sidebar chunks and routes returned `forbidden` | `dsh.tauri.localhost` was absent from `ctx.webRuntime.trustedHosts` | Desktop patched Connection-level configuration although independent route owners use WebRuntime authority |
| Models and plugin settings reported that settings were unavailable | The alias did not satisfy the literal loopback/Host-ownership decision | Desktop treated URL reachability, trust and browser Host privilege as one concept |
| `dsh-tauri-session` could reject the plugin graph | The artifact registered `settings.section` directly before the owner table existed | Plugin activation relied on incidental RC load order rather than the target slot injection contract |
| Switching or a missing core path could stop or crash the shell | Core selection mutated directories and error paths escaped lifecycle handling | Core storage, selection, plugin projection and process state were coupled in one mutable operation |
| GitHub sign-in or network behavior appeared during plugin setup | Startup installed moving Git sources or registry packages | Runtime installation was used as deployment; artifacts lacked pinned, offline, family-specific provenance |
| RC accepted no alpha session and displayed a validation error | The session contained events unknown to RC | This is an intentional prerelease format boundary, not a Desktop plugin defect |

The core update made authentication, package exports, slots and session vocabulary genuinely incompatible. The large debugging cost did not come from those changes alone; it came from Desktop spreading core assumptions across workflow, React, profiles, mutable directories and unversioned plugin installs.

## Architecture changes

### Immutable core slots

Each packaged core lives in `dependencies/cores/<tag>`. `dependencies/active-core` selects the active artifact. Switching validates the target first, stops only the owned process, updates the pointer and settings, rebinds plugins, and rolls back pointer, settings, plugin projection and service state on failure.

### Version-owned adapter families

`DshAdapter` resolves the installed package version to `legacy-web` or `authenticated-web-v1`. The adapter owns launch arguments, optional `--no-open`, the readiness URL interpretation, authenticated WebView navigation and the private WebRuntime overlay. Unknown future generations fail before launch instead of inheriting the newest known behavior.

### Clean product profile

`product-zhiliao-zhihuiguan` starts from official `dsh-base` and `dsh-web-app`. Desktop compatibility rows live in `dsh-adapters/<family>.cordis.yml`, not in the official core, official Web profile or user `cordis.patch.yml`.

### Managed plugin projection

Desktop persists selected logical plugin IDs. Build preparation produces `legacy-web` and `authenticated-web-v1` artifacts from pinned package versions or Git revisions. Core switching installs the selected family into content-addressed profile paths and runs a static compatibility gate before launch.

### Explicit embedded Host ownership

The authenticated adapter extends the authoritative `web-runtime.trustedHosts` list with `dsh.tauri.localhost`. A WebView initialization script declares Host ownership only for that application-controlled authority; it does not grant arbitrary remote origins loopback privilege.

### Diagnostics as a product interface

The shell records frame readiness and surface checks through IPC, exposes a read-only diagnostics snapshot through Tauri and a standalone CLI, and shares `surface-contracts.json` with the WebView2 traversal script. Error documents, Loader failures, missing plugin IDs, failed lazy resources, unavailable settings and sidebar failure text become command-line assertions.

## Plugin results

The accepted boot graph contains `dsh-tauri`, `dsh-tauri-ui`, `dsh-tauri-worktree`, `dsh-tauri-panel`, `dsh-tauri-panel-extension`, `dsh-tauri-session`, `dsh-tauri-rightclick`, `dshmarket`, `dsh-better-sidebar`, and `dsh-notification` on the alpha adapter when selected.

`dsh-win-terminal-inspector` remains a legacy-only preset because the alpha core supplies the relevant Windows behavior. Its absence from the authenticated family is an explicit capability decision, not a failed installation.

The Desktop matrix proves composition, resource loading and declared surfaces. Plugin repositories remain responsible for destructive domain actions such as Worktree creation, archive mutation, terminal process behavior and notification delivery.

## Verification

The final implementation passed 292 Rust library tests, TypeScript type checking, JavaScript syntax checking, diff hygiene, the alpha real-frame surface matrix, and the retained RC matrix. The RC run reported the expected incompatible alpha session refusal while the shell remained responsive.

The matrix asserts the real boot graph, authenticated frame readiness, every declared lazy resource, Models and plugin settings pages, Better Sidebar built-in tabs, Tauri panel surfaces, and the absence of known Loader, authorization and settings failure signatures.

## Remaining debt

The semver-to-family table is compiled into Desktop. A future capability manifest should make readiness, authentication, client ABI, Loader and session generations explicit in the packaged DSH artifact.

The build currently performs narrow transformations on older plugin artifacts, including the Store import and one slot registration. These transforms require removal when compatible upstream plugin versions are pinned; expanding them into a general JavaScript rewrite layer is prohibited.

The surface matrix verifies non-destructive integration paths. It does not replace package-owned end-to-end tests for state-changing plugin operations, nor does it establish cross-prerelease session compatibility.

## Guidance for the next adapter

Start with the clean official target and compare its declared or observed protocol with `authenticated-web-v1`. If only package versions change, rebuild and verify the same family. If readiness, authentication, client ABI, Loader or session generation changes, add a new family and a new version record before modifying workflow or UI code.

Treat every repeated fix outside the adapter, plugin projection or diagnostics inventory as evidence that the compatibility boundary is incomplete. The objective is not to preserve Desktop's old assumptions; it is to make Desktop consume DSH's current public contracts with the same discipline expected from a first-party shell.
