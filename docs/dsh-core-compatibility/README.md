# DSH 内核兼容演进

## 摘要

本目录记录 Deepseek Harness Desktop 如何跟进 DSH 的破坏性版本。索引文档保存稳定的兼容架构；每个以版本命名的记录保存该内核的上游更新、实际冲突、责任分析、实现决策、验证证据和剩余债务。

## 目的

Desktop 将 DSH 视为独立演进的产品，而不是需要冻结或原地打补丁的实现细节。一次适配必须遵循目标内核的公开契约和安全模型，保持官方内核制品不可变，并留下足够证据，使其他维护者或编码 Agent 能够复现决策。

每份版本记录回答六个问题：上游更新了什么、哪些 Desktop 或插件假设发生冲突、每项冲突为何出现、哪些工作不可避免、哪些工作暴露了 Desktop 架构债务，以及哪项架构更改能够降低下一次更新成本。

## 架构

1. `dependencies/cores/<tag>` 保存一个不可变的官方或本地打包 DSH 制品；`dependencies/active-core` 只选择槽位，不复制或修改内核。
2. `product` 从官方 Web bundles 初始化，并将用户配置与 Desktop 兼容行为分离。
3. `src-tauri/resources/core-compatibility.json` 是运行时选择、插件制备和功能面矩阵共同消费的唯一版本能力表；`service/core_compatibility.rs` 拒绝表中不存在的版本。
4. `plugins/dsh-v<内核版本>/plugin-set.json` 独立声明每个已验收 tag 的内置与预设插件来源，版本目录同时拥有自己的制品适配入口。切换内核时，逻辑插件选择只投影到该 tag 的制品，不能复用另一 tag 的插件目录。
5. 壳只消费稳定的运行结果。内核切换只有在目标进程、认证运行时、WebView 路由和目标插件客户端图全部报告同一精确版本后才完成；workflow 负责建立这些状态，React 只响应“运行时已替换”事件，不按 DSH 版本分支。
6. 机器可读诊断和真实 frame 功能面矩阵验证启动图、设置页、延迟资源和侧栏贡献，不依赖人工点击。
7. `dsh-desktop-control` 通过带令牌的回环控制面调用 Desktop 权威 service，输出结构化轨迹、延迟和失败码。它随独立 DSH 进程运行；可在保留 Harness 的情况下受控退出 Desktop，壳崩溃后仍可读取落盘轨迹并恢复，恢复后的外壳接管原 Harness 进程。debug、release 和安装版共享一个操作系统单例锁，禁止并发实例覆盖这些状态。
8. 每个精确 tag 目录拥有自己的 `dsh-desktop-control` 完整源码。客户端插件必须导出 `./package.json`，因为 DSH 客户端模块扫描器以该导出读取 `dsh.client` 声明；制品门禁会拒绝缺失导出的包。

## 兼容责任

内核负责 CLI 语法、就绪输出、认证、Host 与 Origin 策略、公开包导出、Loader 语义、slot 声明、RPC 协议和持久化会话词汇。Desktop 必须适配这些契约，不能为了保留旧集成而削弱它们。

Desktop 负责内核选择、进程监管、WebView 导航、产品 profile 组合、插件制品选择、失败呈现、回滚和兼容诊断。即使某项上游更新暴露了这些问题，该范围内的失败仍属于 Desktop 缺陷。

插件作者负责使用公开 DSH 包、声明 peer dependencies、遵循 slot 贡献时序并保证功能行为。两个内核的公开客户端服务或生命周期存在重大差异时，Desktop 必须在各自的 `plugins/dsh-v<内核版本>/` 中维护独立插件源码或固定来源，不能在共享插件中增加跨世代条件分支。对固定发布制品的 JavaScript 转换只能存在于对应 tag 的制品入口，并应由该目录中的源码实现替换。

## 适配方法

1. 在不启用 Desktop 插件的情况下构建并运行干净的官方目标 profile。记录 CLI 参数、stdout 就绪信号、认证交换、Cookie 策略、可信 Host 来源、浏览器 Host 权限判定、启动图、设置命名空间、公开客户端包、slot 声明、RPC 路由和持久化会话行为。
2. 将观察结果与最新已验收记录比较。把每项差异分类为上游契约更新、Desktop 自有集成缺陷、插件自有不兼容或预发布阶段的有意限制。
3. 为内核增加一条精确记录，并由可复用协议能力组合该记录。不得使用开放 semver 范围，也不要把版本判断分散到 workflow、React、profile 或插件中。
4. 新建 `plugins/dsh-v<内核版本>/`，显式列出该 tag 的全部插件来源。公开服务或生命周期发生重大变化时，在新目录开发该版本插件；只有机械且有精确断言的发布制品转换可以暂存在该目录的制品入口。共享构建器不得包含内核版本判断。
5. 启动前运行静态兼容检查，再对新内核和所有保留内核执行同一套运行矩阵。矩阵必须双向切换，并在每次切换后验证后端版本、认证路由、客户端 ABI、插件功能面和状态变更行为属于同一个精确 tag。
6. 在版本文件中记录实测证据和剩余债务。不能根据截图或仅壳启动成功判定验收。

## 验收标准

只有干净官方 profile 能启动、Desktop 产品 profile 的 Loader 进入 live、全部声明的管理插件进入真实启动图、全部声明的延迟资源成功返回、设置与侧栏功能面打开时没有已知故障特征、失败操作不会破坏壳、切换到所有保留内核均不会导致 Desktop 崩溃时，内核才通过验收。

`dsh-desktop-diagnostics snapshot` 报告所选槽位、包版本、来源证明、profile 兼容性和最近的 frame 报告。`dsh-desktop-control` 内置插件可直接读取同一快照、运行并发压测、提取日志与 trace，并在壳崩溃后恢复它。`pnpm verify:feature-tests` 保证功能 command 与测试接口规约同步；`pnpm diagnostics:select-core <version>` 通过 Tauri IPC 切换已安装测试目标并等待健康；随后由 `pnpm diagnostics:surface` 遍历声明的真实 frame 功能面，并在断言失败时返回非零退出码。内核包和每个插件仍负责各自领域变更与端到端行为。

## 长期方向

适配成本应逐渐收敛为三项有界工作：描述新内核协议、针对公开包构建插件、扩展兼容矩阵。如果每次都需要修改进程生命周期、React 状态、用户 profile 或已安装内核文件，就说明架构仍有缺陷，必须在同一次适配中完成结构修正。

Desktop 现在拒绝所有没有精确测试记录的内核，并通过诊断暴露 Web 启动协议、客户端 ABI、slot 协议、会话格式和插件制品集。下一步目标是让上游打包制品携带这些能力声明；精确版本记录继续作为来源证明和验收矩阵键。
