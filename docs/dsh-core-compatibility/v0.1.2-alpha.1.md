# DSH `0.1.2-alpha.1` Desktop 适配记录

## 摘要

本记录覆盖 Desktop 从保留内核 `0.1.1-rc.2` 迁移到 `0.1.2-alpha.1` 的过程。目标版本引入了 Web 认证启动、拆分后的客户端包图、更严格的扩展注册和 fail-closed 持久化数据读取。这些变化暴露了 Desktop 对 URL、Host 所有权、可变内核目录、无版本插件、profile 补丁和人工验证的错误假设。

## 内核更新

### Web 认证就绪

Web bundle 会等待 Loader 结算和 Connection 服务，通过 `connection.authenticatedUrl()` 创建进程 token URL，将该 URL 输出为就绪信号，并把认证 URL 交给浏览器。认证交换建立 HttpOnly `SameSite=Strict` Cookie；未执行交换的干净源 URL 不是已认证应用会话。

这是合理的内核安全增强。监管进程必须消费输出的 URL，但不能记录或持久化 token；必须为 Cookie 保持同站导航，并区分供展示的干净服务 URL和携带凭据的 WebView URL。

### 客户端包拆分

单体 `@deepseek-ai/dsh-client-runtime` 包已移除。Store 基础设施迁移到 `@deepseek-ai/dsh-client-store`，Session、Workspace、Conversation、Chat、Approval 等职责迁移到各自领域包。API Proxy 传输也被 Connection 自有和领域 Remote 接口取代。

因此，针对 `@deepseek-ai/dsh-client-runtime/client` 编译的插件无法在目标包图中激活。包名替换只能桥接狭窄的 Store 导入；依赖已删除 Runtime 行为的插件必须从源码迁移到新的领域所有者。

### Loader 与 slot 所有权

Client modules 和 UI slots 依赖明确的所有者表，并通过 `ctx.slots.inject()` 延迟贡献。贡献者在声明所有者到达前直接注册 `settings.section` 时可能被拒绝激活，而不是依赖偶然加载顺序静默成功。

这项更新使扩展所有权具有确定性。插件制品必须声明负责物化客户端模块的包，并通过受支持的 injection 路径向延迟声明的 slot 贡献。

### 工作区导航服务

目标版本由 `uiWorkspace` 统一负责工作区连接、新会话导航和归档。替换官方 Sidebar 的插件必须调用 `uiWorkspace.startSession()`；RC 使用的 `workspaces.startSession()` 不再属于目标版本的客户端服务。

### Host 信任与浏览器权限

目标版本将 WebRuntime authority 与 Connection 浏览器权限分开。路由所有者读取 `ctx.webRuntime.trustedHosts`；设置持久化和 Host API 访问依赖 Connection 对浏览器是否持有本地 Host 的判断。嵌入式别名不会自动等价于字面值 `127.0.0.1` 源。

因此 Desktop 必须分别声明两个事实：DSH 接受 `dsh.tauri.localhost` 作为可信 runtime authority，嵌入式浏览器持有这个只监听回环地址的 Host。只设置 Connection 路由值不会更新路由所有者；只设置 runtime 信任不会授予设置持久化权限。

### 持久化会话词汇

目标版本按照必需词汇读取持久化会话事件，并拒绝未知事件类型。预发布版本线不承诺跨版本会话格式，因此 `0.1.1-rc.2` 可能拒绝 `0.1.2-alpha.1` 写入的会话。

Desktop 必须展示拒绝信息，但不能崩溃或改写事件。静默转换会虚构内核语义，使后续恢复更不可靠。

## 实际冲突

| 现象 | 直接原因 | 根因 |
| --- | --- | --- |
| 启动后出现 `ERR_CONNECTION_REFUSED` 或空白壳 | Desktop 在认证就绪 URL 可用前发起导航 | 生命周期把端口监听当作完整 Web 就绪，并用同一个 URL 承担展示和认证导航 |
| 插件 Loader 报告 `dsh-client-runtime/client` 缺少模块表 | RC 时代插件 bundle 导入了目标版本已删除的包入口 | 插件没有按客户端 ABI 世代固定并构建；Desktop 仅根据包名假设 npm 包兼容 |
| Better Sidebar chunks 和路由返回 `forbidden` | `ctx.webRuntime.trustedHosts` 不包含 `dsh.tauri.localhost` | Desktop 修改了 Connection 层配置，但独立路由所有者使用 WebRuntime authority |
| 模型和插件设置提示设置不可用 | 别名不满足字面回环/Host 所有权判断 | Desktop 把 URL 可达性、信任和浏览器 Host 权限视为同一概念 |
| `dsh-tauri-session` 可能拒绝整个插件图 | 制品在所有者表存在前直接注册 `settings.section` | 插件激活依赖 RC 的偶然加载顺序，而不是目标 slot injection 契约 |

| 切换内核或内核路径缺失会停止服务或使壳崩溃 | 内核选择会移动目录，错误越过生命周期处理 | 内核存储、选择、插件投影和进程状态耦合在一次可变操作中 |
| 插件设置期间弹出 GitHub 登录或出现网络行为 | 启动过程安装了浮动 Git 来源或 registry 包 | 将运行时安装当作部署；制品缺少固定、离线、按世代区分的来源证明 |
| RC 无法接受 alpha 会话并显示校验错误 | 会话包含 RC 不认识的事件 | 这是有意的预发布格式边界，不是 Desktop 插件缺陷 |

## 架构更改

### 不可变内核槽位

每个打包内核位于 `dependencies/cores/<tag>`。`dependencies/active-core` 选择活动制品。切换会先校验目标，只停止自有进程，更新指针和设置，重新绑定插件；失败时回滚指针、设置、插件投影和服务状态。

### 精确内核兼容记录

`core-compatibility.json` 是 Rust 运行时选择、插件制备和运行矩阵共同使用的唯一表。记录分别声明 Web 启动、客户端 ABI、slot、工作区导航、归档和会话格式协议。`CoreCompatibility` 只接受其中经过测试的 `0.1.1-rc.2` 和 `0.1.2-alpha.1` 记录；未知版本在启动前失败，不会从开放 semver 范围继承行为。

### 干净产品 profile

`product` 从官方 `dsh-base` 和 `dsh-web-app` 初始化。Desktop 兼容行位于 `dsh-compatibility/web-launch-<protocol>.cordis.yml`，不进入官方内核、官方 Web profile 或用户 `cordis.patch.yml`。

### 管理插件投影

Desktop 持久化选中的逻辑插件 ID。`plugins/dsh-v0.1.1-rc.2/` 与 `plugins/dsh-v0.1.2-alpha.1/` 分别声明完整插件来源并拥有独立制品入口；共享 prebuild 只执行下载、构建和复制，不包含内核版本条件。切换内核时，将所选 tag 的制品集安装到内容寻址 profile 路径，并在启动前运行静态兼容门禁。

RC2 控制插件只调用 `workspaces`，alpha 控制插件只调用 `uiWorkspace`。Panel、Session 或其他插件遇到无法通过公开 API 小幅调整的破坏性变化时，必须在目标 tag 目录维护独立源码并更换该目录的 `spec`，不能让共享插件承担跨世代分支。构建会删除兼容表之外的旧制品目录，插件门禁也拒绝额外版本目录。

启动时仍会遍历全部内置插件和所选预设插件，重新计算制品指纹、检查精确内核兼容记录、核对 profile 依赖来源并读取 `node_modules/<包名>/package.json`。只有来源或真实入口不一致时才执行 `dsh plugin add`；同一内核的热启动不运行 pnpm，也不减少 Loader 启动图中的插件。

早期实现把安装参数 `<包名>@link:<路径>` 直接与 pnpm 清单值 `link:<路径>` 比较。两者表达同一来源，但字符串前缀不同，导致每次启动都把健康的 8 个内置插件判为 `dep_ok=false`；所选社区插件也在每次启动无条件重装。修复后的比较先分离可选包名与 `link:`/`file:` 来源，再规范化路径；社区插件则只在内容寻址制品槽位与当前内核制品集不一致时重绑定。这部分工作量来自 Desktop 缓存模型错误，不是内核破坏性更新所必需。

启动日志用稳定的 `STARTUP_PHASE`、`INTERNAL_PLUGIN_CACHE_HIT`、`MANAGED_PLUGIN_CACHE_HIT` 和 `MANAGED_PLUGIN_REBIND` 记录插件核验、内核依赖清理、完整性复检、进程创建及 alpha 认证 URL 发布耗时。实测 alpha 热启动中，8 个内置插件核验约 55 毫秒，3 个所选社区插件核验与兼容门禁约 154 毫秒，两批均安装 0 个；DSH 进程创建到认证 URL 约 2.4–2.5 秒。前端启动探测从 2 秒固定间隔改为 250 毫秒、保持约 10 秒总预算，因而只缩短“已经就绪但尚未发现”的等待，不改变 Loader 完整性条件。

### 明确的嵌入式 Host 所有权

`token-cookie-v1` 启动能力将 `dsh.tauri.localhost` 加入权威 `web-runtime.trustedHosts` 列表。WebView 初始化脚本只为该应用控制的 authority 声明 Host 所有权；它不会为任意远程源授予回环权限。

debug 壳使用 `desktop.tauri.localhost` 加载 Vite，release 壳使用 `tauri.localhost`。二者都与 `dsh.tauri.localhost` 属于同一站点，因此开发矩阵和发布构建接受相同的 `SameSite=Strict` Cookie；debug 若回退到普通 `localhost`，认证故障会被误判成插件或 Loader 故障。

### 将诊断作为产品接口

壳通过 IPC 记录 frame 就绪和功能面检查，通过 Tauri 和独立 CLI 暴露只读诊断快照，并让 WebView2 遍历脚本共享 `surface-contracts.json`。错误文档、Loader 失败、插件 ID 缺失、延迟资源失败、设置不可用和侧栏失败文本都成为命令行断言。

### 独立代理控制面

Desktop 在随机回环端口发布带随机令牌的逐行 JSON 控制协议，连接记录仅落在应用私有数据目录。操作直接复用内核、档案、生命周期、诊断和日志 service；协议层不复制业务规则。每次调用写入带 trace id、操作名、进程号、耗时、结果和稳定错误码的 JSONL 轨迹，敏感参数与认证令牌不进入轨迹。

`dsh-desktop-control` 作为内置 Host 插件运行在独立 Harness Node 进程中，提供状态、只读调用、诊断并发压测、受控退出和外壳恢复工具。受控退出只消费一次“保留 Harness”标志，普通退出继续回收子进程，避免改变既有生命周期语义。插件从 Desktop 管理的 PID 文件读取 Harness 身份，并持续写入仅当前用户可读、与 Harness PID 和监听端口绑定的恢复记录；外部测试进程或重复加载不能用自身 PID 污染接管依据。alpha 的 Connection service 可在记录中补充进程级认证 URL，RC 则只记录存活信息；同一 PID 和端口的无 Connection 刷新保留已有 URL，身份变化才清除，避免热重载破坏恢复凭据。Desktop 受控退出或崩溃时，插件仍持有连接记录、可执行文件路径和轨迹路径；它重新拉起外壳并设置恢复标志，新外壳再次校验 PID、监听端口和可选认证 URL 后接管原 Harness，而不是把负责恢复的进程当作孤儿结束。令牌使用操作系统随机源生成，不会进入日志或控制轨迹。

单例锁不再区分 debug 和 release。两种构建与安装版共享同一应用标识、数据目录、控制端点和 Harness 所有权，允许开发构建绕过单例会制造两个权威写入者。`instance.info` 暴露当前单例身份；`pnpm stress:single-instance` 并发启动带内部探针参数的二级进程，要求全部快速退出、主 PID 和端点不变。探针不会抢占窗口焦点，普通二次启动仍唤醒已有窗口。

Windows 实测包含 500 次、并发 32 的热重复启动，失败数为零且主 PID 不变；无主进程时 64 个 release 同时抢锁，最终只保留一个进程且控制端点指向该 PID。抢锁后继续执行 1,000 次、并发 64 的诊断快照，成功 1,000 次、失败零次。以上压测使用 release 制品，结束后仅保留唯一 release 实例。

内核列表曾把活动槽位 `0.1.2-alpha.1` 错标为历史下载记录 `0.1.1-rc.2`。正向诊断读取槽位内 package version，因此未发现列表投影丢失；这是测试只验证活动运行状态、没有验证反向集合不变量造成的覆盖缺口。修复后 `active-core` 是活动 tag 的唯一权威来源，槽位清单决定实际版本，历史 `dsh_pkg_tag` 不能覆盖活动身份。功能面矩阵和内核选择脚本同时断言 alpha、rc2 各出现一次且已安装、恰好一个活动行与实际运行版本一致，并执行 `alpha → rc2 → alpha` 往返。

活动内核指针使用同目录临时文件、文件同步和原子替换发布。Windows 在读者短暂持有文件句柄时可能拒绝替换，因此写入方对共享冲突执行有界重试；读者只能观察到完整旧 tag 或完整新 tag。并发测试持续读取指针并交替写入两个版本，拒绝文件缺失、空值和截断值。内核解析失败日志同时记录来源、活动槽位、安装根、CLI 入口和包清单是否存在，使 `CORE_COMPATIBILITY_VERSION_MISSING` 可以从日志直接定位到选择层或制品层。

`feature-test-contracts.json` 将全部 Tauri command 按功能域绑定到机器接口。`pnpm verify:feature-tests` 对 command 的新增、改名和删除执行双向检查，并验证规约引用的控制操作确实存在。今后每项功能变更必须同时更新测试接口、结构化断言和可关联日志，不能把人工点击或 computer-use 作为唯一验收手段。

规约版本 v2 进一步要求每个功能域登记仓库中真实存在的机器行为断言。门禁会验证断言来源及其稳定标识，避免把“IPC 已注册”误当成“功能可用”。会改变状态的测试读取操作前后的权威 ID 或集合，可逆操作还必须回滚；内核切换执行正向和反向往返。

功能面矩阵通过 DSH RPC 自动创建或复用隔离测试工作区和空会话，再写入客户端公开的会话选择状态后重载 frame。侧栏测试因此具备确定的会话前置条件，不再依赖维护者先手工创建会话；Vitest 的发现范围固定在 Desktop `test/`，不会把打包插件自带的独立 Node 测试误当成空 Vitest suite。

## 插件结果

在 alpha 内核中，选中后通过验收的启动图包含 `dsh-tauri`、`dsh-tauri-ui`、`dsh-tauri-worktree`、`dsh-tauri-panel`、`dsh-tauri-panel-extension`、`dsh-tauri-session`、`dsh-tauri-rightclick`、`dshmarket`、`dsh-better-sidebar` 和 `dsh-notification`。

`dsh-win-terminal-inspector` 保留在 `dsh-v0.1.1-rc.2` 制品集中，因为 alpha 内核已提供相关 Windows 行为。`dsh-v0.1.2-alpha.1` 不包含它属于明确能力决策，不是安装失败。

Desktop 矩阵证明组合、资源加载和声明功能面。插件仓库仍负责 Worktree 创建、归档变更、终端进程行为和通知投递等破坏性领域操作。

## 验证

内核适配通过 Rust 库测试、Desktop Vitest、TypeScript 类型检查、生产构建、JavaScript 语法检查、插件制品门禁和双内核运行矩阵。新会话回归由 `dsh-desktop-control` 的浏览器客户端接口执行，不依赖 DevTools：测试先选中非空会话，再点击实际 Panel 按钮，并断言按钮调用一次当前内核的导航服务、当前 Session ID 改变且目标会话为 `blank=true`。

矩阵断言真实启动图、认证 frame 就绪、全部声明的延迟资源、模型与插件设置页、Better Sidebar 内置标签、Tauri panel 功能面，以及不存在已知 Loader、授权和设置失败特征。

启动性能回归额外要求同一内核连续启动的第二轮出现内置插件和管理插件缓存命中，且没有插件安装命令；`rc2 → alpha` 切换必须执行制品集重绑定，随后的 alpha 启动再次缓存命中。内核往返脚本将“目标已经激活”作为幂等路径，避免测试工具把重复选择误报成产品故障。切换成功还要求诊断中的 WebView 路由与功能面均为 `ready`，并且二者报告的内核版本等于目标版本；仅有 HTTP 健康响应不构成切换完成。

## 剩余债务

精确版本到能力的映射仍编译在 Desktop 中。未来的上游能力清单应在打包 DSH 制品中发布就绪、认证、客户端 ABI、Loader 和会话世代，同时 Desktop 保留精确测试版本白名单。

alpha tag 的制品入口仍对固定插件版本执行少量机械转换，包括 Store 导入和一处 slot 注册。转换由 `plugins/dsh-v0.1.2-alpha.1/` 单独拥有，RC2 制品入口不会执行这些规则。上游插件发布 alpha 原生版本后应在该 tag 的清单中替换来源并删除对应转换；禁止把规则移入共享 prebuild。

alpha 的 Panel 制品包含 `uiWorkspace.startSession()` 且不包含旧调用，RC2 的 Panel 制品只包含 `workspaces.startSession()`。同一双向断言也覆盖控制插件，防止某个 tag 的实现进入另一个 tag 的插件集合。

功能面矩阵验证非破坏性集成路径。它不能取代插件自有的状态变更端到端测试，也不能建立跨预发布版本会话兼容承诺。

## 故障复盘

### 发布壳黑屏

黑屏的直接原因是 Tauri 资源压缩缓存中存在损坏的 JavaScript 压缩项。发布壳找不到正确脚本时回退到 `index.html`，脚本请求因此得到 `text/html`；React 没有挂载，DSH frame 也不会创建。DSH 服务、认证 URL 和插件 Loader 均可保持健康，所以只检查端口、健康接口或 DSH 日志无法定位该故障。

排查最初从 DSH 服务、iframe 认证和插件生命周期开始，因为当时最早的机器观测点位于 React 和 DSH frame 之后。页面未挂载时这些探针都不存在，多个下游假设会呈现同一个空白结果。开发壳还会直接使用 Vite 资源，不能证明发布 EXE 的内嵌资源有效；普通构建成功也不能证明压缩缓存内容可解码。

根因在壳调用链被拆成内嵌资源查找、MIME 与 fallback、文档创建、DOM 就绪、React 挂载、DSH frame 就绪六个独立阶段后确定。`shell.status` 不依赖 React 或 DSH，可直接报告脚本是否存在、是否回退为 HTML，以及当前进程是否记录 `react-mounted`。构建准备会校验并清除损坏的 Tauri 压缩缓存，发布壳门禁会启动真实 EXE 并等待资源完整与 React 挂载同时成立。

仅等待 React 挂载仍不能证明产品已启动。发布壳门禁会连续执行三轮完整冷启动；每轮要求控制端点属于新 PID、活动内核版本与精确兼容记录一致、Harness 健康、当前进程发布新的 WebView 路由与功能面报告。前两轮通过 `desktop.shutdown` 停止 Harness、退出 Desktop 并等待 PID 消失后才启动下一轮。保留 Harness 的 `desktop.exit` 只用于崩溃恢复验证，不能作为冷启动测试的清理动作。

### 新建会话和归档无可见响应

新会话无响应的直接原因是 `dsh-tauri-panel@0.5.2` 替换了官方 Sidebar，却仍调用 RC2 的 `workspaces.startSession()`。目标内核的官方 Sidebar 已迁到 `uiWorkspace.startSession()`，所以直接调用官方导航服务可以成功，Panel 按钮却不会改变 Session Store。浏览器客户端探针记录的按钮 class 为 `dshp-newSession`，点击后当前 `uiWorkspace` 调用次数为零，从而把故障定位到插件表面，而不是内核后端或 Session Store。

alpha 内核会复用当前空白会话。点击“新建会话”后，会话名称和页面外观可能保持不变；只检查文本或节点是否变化会把正确的幂等行为误报为无响应。归档同名空白会话后，内核可以立即创建另一个同名空白会话，视觉结果同样不能证明归档是否发生。

归档还存在所有权冲突：alpha 内核提供原生会话归档，旧插件制品同时携带基于 DOM 和 React Fiber 的拦截逻辑。该逻辑依赖旧 Web 实现细节，不应覆盖新内核的原生能力。精确内核兼容记录因此声明归档协议；alpha 使用 `core-native-v1` 并移除旧拦截 effect，RC2 保留 `plugin-workspace-patch-v1`。

客户端动作接口会记录按钮、导航服务调用次数、操作前后 Session ID、`blank` 状态、Workspace ID 和 Workspace 的 `sessionIds`。归档测试对比操作前后的归档集合，并执行取消归档恢复测试数据。断言针对权威状态，不依赖名称、列表重绘时机或维护者的人工观察。

### 测试为何没有一次发现

旧门禁覆盖的是接口存在性和当前快照，不是完整行为。原有“新会话”断言从已经处于空白会话的状态开始，只验证点击后 ID 没变，既没有建立“非空会话”前置条件，也没有证明按钮进入导航服务。它因此在 Panel 调用不存在的旧方法时仍可能通过。正向内核快照也不能发现反向切换、集合投影或回滚错误。旧发布壳测试只等待 React 挂载，并通过保留 Harness 的退出路径清理壳，后续运行实际复用了热服务，因此无法发现活动内核选择与冷启动的竞争。

测试体系按故障层级分工：Vitest 和 Rust 测试验证纯逻辑与失败处理；构建门禁验证每个版本制品使用正确服务；发布壳门禁验证内嵌资源与 React；客户端动作接口验证按钮到 Store 的因果链；内核往返验证 RC2 和 alpha 分别使用自己的导航协议；独立控制面压测验证单例、诊断并发和崩溃后可观测性。`feature-test-contracts.json` 将这些断言与功能域绑定，使功能代码变化时可机械发现缺失或失效的测试入口。

### 反向内核切换保留旧客户端

RC2 切换到 alpha 后曾出现后端已经是 alpha、页面仍运行 RC2 客户端的混合状态。两个内核复用同一 WebView 和端口，旧实现只等待监听端口恢复便返回成功；壳随后读取到回退 URL，或者继续保留旧 frame。HTTP 健康只能证明某个服务正在响应，不能证明认证 URL 已发布，也不能证明新 frame 的 Loader 和插件客户端图已经建立。

切换事务现在依次完成精确插件集投影、目标内核启动、目标认证运行时就绪，再发布“运行时已替换”事件。壳收到事件后重新读取权威 URL 并更换 frame key。命令行选择工具继续等待新 frame 的路由报告和功能面报告，且两份报告必须携带目标内核的兼容记录。由此，调用方拿到成功时，后端、profile、认证会话和客户端插件图属于同一个 tag。

该问题也暴露了测试假阳性：单向 `alpha → rc2` 不能覆盖认证协议从无到有的方向，端口健康检查也不能覆盖 Client ABI。保留内核矩阵因此必须至少执行 `alpha → rc2 → alpha`，并在每一站运行真实的新建会话和归档状态迁移，而不是只比较内核列表或页面标题。

### 用户诊断日志

帮助菜单的“复制诊断日志”生成脱敏诊断包，包含 Desktop、DSH 与 Node 版本、精确内核能力、插件兼容报告、壳资源、React 与 frame 阶段、功能面结果、控制调用轨迹以及服务、前台和后台日志尾部。应用数据目录、DSH 数据目录、活动档案和常见认证字段会替换为占位符。

服务、后台和前台日志各限制为 5 MiB 并保留三个备份；控制轨迹限制为 5 MiB 并保留一个备份。复制操作只读取每个文件最多 256 KiB 的尾部。前端日志以 200 毫秒为周期批量传输，队列和单批均限制为 256 KiB，错误日志立即刷新；Rust 每批只获取一次锁并执行一次文件刷新。

## 下一版适配指导

从干净官方目标开始，将声明或观察到的能力与 `0.1.2-alpha.1` 记录比较。增加一条精确版本记录，复用未变化的协议能力 ID，只为已变化协议创建新 ID，然后构建匹配的 `dsh-v<version>` 插件制品集，再考虑修改 workflow 或 UI 代码。

如果适配仍反复修改内核兼容、插件投影或诊断清单之外的代码，就应视为兼容架构仍不完整。目标不是保存 Desktop 的旧假设，而是让 Desktop 以第一方壳应有的纪律消费 DSH 当前公开契约。
